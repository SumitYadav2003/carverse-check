Two sources of data

The car's own history comes live from the DVSA MOT history service each time you check a plate. It's stored in memory for up to an hour so repeat visits are quick.

The comparisons come from DVSA's anonymised MOT data: one record for every MOT test carried out in Great Britain in 2024, with the vehicle's make, model, first-use date and mileage, and every defect recorded. It has no number plates, so it can't be linked back to a particular car.

The pipeline

The anonymised files are processed on the author's computer, and only the small summary tables are copied to the website.

  1. Load. Every file is loaded into DuckDB exactly as published, as text, with a fingerprint (SHA-256) of each file. Re-running skips files already loaded, and a file DVSA republishes with changes is reloaded in full.
  2. Clean and model. dbt models clean and type the data, remove duplicates and build a star schema: one fact table of tests ({{ facts.tests }} rows), one of defects ({{ facts.defects }} rows), and dimensions for vehicle models and defect types.
  3. Summarise. Mart tables work out failure rates, defect categories and mileage spreads for each make, model and year of first use, with the statistics described below.
  4. Test. dbt data tests and unit tests run on every build. If one fails, the figures don't reach the website.
  5. Publish. The marts are copied into the website's database in a single transaction, so the site never shows a half-loaded state.

A small set of made-up data in the same format, with the same quirks, runs through the whole pipeline on every code change (GitHub Actions).

Cleaning the data

The published files needed more work than their user guide suggests. What we found, and the rule applied to each:

  • Repeated header lines inside the data. Removed.
  • Exact copies. About 35% of test result rows are exact copies of another row. Copies are collapsed into one test.
  • Copies that disagree. 829,687 tests have copies that differ, mostly in vehicle details. Where copies disagree about a value, that value is treated as unknown rather than guessed, and the test is flagged. The year of first use is kept whenever the copies agree on it.
  • Repeated defects. Each distinct defect is counted once per test.
  • Awkward text. A few values contain commas or escaped quote marks, which break naive file reading. The file format is set explicitly, and any line that still can't be read is set aside and counted, with a limit of 0.1% per file.

The statistics

Like-for-like groups

Each group is one make, model and year of first use, using initial tests of class 4 vehicles (cars and light vans), as in DVSA's own statistics. A group needs at least 30 tests to appear. Defect categories need at least 100, because they split a group into smaller pieces.

A likely range for every rate

Each failure rate comes with a 95% range, the Wilson score interval (Wilson, 1927). Unlike the textbook "plus or minus" formula, it stays between 0% and 100% and behaves well for small groups.

Adjusted estimates for small groups

A group with 30 tests can show a failure rate 10 points away from its true value just by chance. The adjusted estimate uses empirical Bayes, an approach going back to Efron and Morris (1975): each group's rate is pulled towards the rate for all cars of its age, strongly when it has few tests and hardly at all when it has many. How strongly depends on how much models of that age genuinely differ, which is measured from the data (see below).

When we say "more often" or "less often"

A model is only described as failing more or less often than its peers when the whole 95% range of its adjusted estimate is on one side of the peer rate, and the gap is at least one percentage point. Smaller gaps can be real but are too small to matter when you're buying a car.

Funnel plots

The chart in each report is a funnel plot (Spiegelhalter, 2005), the kind used to compare hospital outcomes. It shows every model of the same age, with limits that are wide for small models and narrow for big ones. Following Spiegelhalter's additive random-effects method, the limits allow for chance and for the normal spread between models, so a dot outside them genuinely stands out.

That method first clips extreme scores before measuring the spread, normally at the 10th and 90th percentiles. In simulations where the true spread was known, that halved the measured spread when every model genuinely differs, which would make far too many models look unusual. Clipping at the 1st and 99th percentiles stayed within about 10% of the truth, with and without extreme models, so that's what we use. The simulation is in the code (pipeline/check_spread_estimator.py) for anyone to re-run.

Odometer rounding check

Montag (2017) adapted the "last-digit test", first used to look for fraud in election results, to find suspicious mileages in used-car adverts. The idea: in genuine readings, the last digit is equally likely to be anything from 0 to 9. If far more readings end in 0, some were rounded or estimated rather than read.

Testing

  • Data tests check every build: unique keys, valid relationships between tables, allowed values, and rules that must always hold, such as every range containing its own rate.
  • A dbt unit test checks the spread calculation against figures worked out separately in Python.
  • The DVSA reconciliation test described above.
  • Website tests cover the checks, the comparison wording, the DVSA connection (without calling DVSA) and every page.

Limitations

  • Comparisons use one year of tests (2024). A model's figures can change from year to year.
  • Groups are matched on make and model as DVSA records them. Different spellings of the same model end up in different groups, and a car whose model is recorded differently won't find its group.
  • Mileages are assumed to be in miles. The anonymised data doesn't record the unit.
  • MOT failure measures a car's condition on the day of the test. It isn't the same as reliability, and owners of some models may maintain them better than others.
